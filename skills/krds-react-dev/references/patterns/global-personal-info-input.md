# 개인 식별 정보 입력

## 개요

개인 식별 정보는 사용자 본인을 포함하여 특정한 개인의 신원을 밝히거나 개인/단체에 대한 기본 정보 확인에 사용되는 모든 정보를 의미한다. 사용자에게 개인 식별 정보의 입력을 요청하기 전에 해당 정보를 반드시 수집해야 하는지 다시 한 번 점검하고, 사용자에게 입력이 필요한 이유를 명확하게 설명하는 것이 좋다.

## 유형

- 이름
- 생년월일
- 성별
- 전화번호

## 사용성 가이드라인

### 공통

- **개인 식별 정보의 수집이 필요한지 확인한다.** 사용자에게 입력을 요청하기 전에 서비스 이용을 위해 반드시 필요한 정보인지 다시 한 번 확인해야 한다.
- **입력이 필요한 데이터의 용도를 명확하게 설명한다.** 입력한 데이터가 어떻게 활용될 것이고 어떤 편의성을 제공할 수 있는지를 사용자에게 명확하게 안내해야 한다.
- **개인 식별 정보 입력 필드에 복사와 붙여넣기를 허용한다.** 데이터 입력에 어려움을 느끼거나 시간이 많이 걸리는 사용자를 고려해 모든 개인 식별 정보 입력 필드에서 복사와 붙여넣기를 제한하지 않아야 한다.
- **기본값을 설정하지 않는다.** 플레이스홀더를 사용하는 경우에는 실제 입력과 쉽게 구분할 수 있도록 한다.

### 이름

- **사용자가 입력할 수 있는 모든 문자의 입력과 표시를 지원한다.** 이름이 다양한 언어로 작성될 수 있음을 고려해 기호·공백을 포함한 모든 문자의 입력을 허용하고 화면에 적절히 표시되도록 해야 한다. 본인인증 등에서 문자 형식이 지정된 경우 제약 사항을 명확하게 설명하고 적절한 대안을 제시해야 한다.
- **이름 입력 필드에 입력 가능한 글자 수를 적절하게 구성한다.** 모든 사용자의 이름을 수용할 수 있는 글자 수를 허용하고 최대 길이에 맞춰 필드 너비를 제공하되, 가장 짧은 이름의 글자 수도 고려해야 한다. 한글 이름 기준 유효성 검사에서 최소 3글자 이상 입력을 요청하지 않도록 유의한다.
  - **피해야 할 사례**: 이름 입력에 단일 텍스트 입력 필드만 사용한다 — 모든 사람의 이름이 일반적인 성/이름 형식에 부합하지 않을 수 있으므로 여러 개의 이름 입력 필드는 신중하게 사용해야 한다.
  - **모범 사례**: 개명한 사용자가 문제없이 이름을 입력할 수 있는지 확인하고, 제약이 있다면 해결 방안을 이름 입력 필드 주변에 제공해야 한다.

### 이름의 로마자 표기 (외국인)

- **외국인 사용자 이름의 길이를 고려하여 이름 입력 필드의 가로 길이(field length)를 충분히 확보한다.** 일반 단일 입력 필드 기준 최소 320~360px 이상을 확보하고, 폼이 단일열이면 가용 폭을 100% 사용한다. 이름이 길어도 필드 안에서 스크롤되거나 전체가 보이도록 처리한다.
- **사용자가 공백을 포함한 이름을 입력하도록 허용한다.** 클라이언트·서버 측 유효성 검사에서 중간 공백을 오류로 처리하거나 자동 제거하지 않으며, "여권에 표기된 이름 전체를 입력하세요. 공백과 '-'를 포함할 수 있습니다." 같은 안내 문구를 제공해야 한다.
- **이름의 대소문자를 정규화하지 않는다.** 여권, 외국인등록증 등 공적 문서와의 일치성을 보장하기 위해 사용자가 입력한 대·소문자 표기를 그대로 저장·표시한다.

### 생년월일

- **생년월일의 입력에 날짜 선택기를 사용하지 않는다.** 날짜 선택기는 사용자가 입력 시점 기준 전·후 날짜를 상대적으로 탐색해야 하므로 이미 명확하게 알고 있는 날짜를 선택하는 데 적합하지 않다.
  - **피해야 할 사례**: 날짜 선택기(캘린더) 사용.
- **연도, 일의 입력에 셀렉트를 사용하지 않는다.** 셀렉트로 제공하면 옵션 수가 지나치게 많아 오히려 입력이 어려워질 수 있다. 다중 입력 필드나 단일 입력 필드를 사용하는 것이 좋다.
  - **피해야 할 사례**: 연도·일 입력에 Select 사용.
- **날짜 입력 형식을 정확하게 안내한다.** 날짜 입력 서식 컴포넌트 가이드라인에 따라 입력 형식을 안내한다.

### 성별

- **특정 성별을 기본값으로 지정하지 않는다.** 입력폼이 로딩되었을 때 특정 성별 옵션이 기본으로 선택되어 있지 않도록 유의한다.
  - **피해야 할 사례**: 특정 성별 사전 선택.
- **'선택 안 함' 옵션을 제공한다.** 성별이 신원 확인에 필요한 정보가 아니라면 필수 입력 항목에서 제외하거나 응답하지 않을 옵션을 제공하는 것이 바람직하다.
  - **모범 사례**: 남성/여성/선택안함 옵션 제공.

### 전화번호

- **활용 용도에 적합한 유형의 전화번호 입력을 요청한다.** 모든 사용자가 모든 유형의 전화번호를 보유하지 않으므로, 인증이나 메시지 발신이 필요하지 않는 한 특정 유형만 허용하는 것은 바람직하지 않다.
  - **피해야 할 사례**: 특정 전화번호 유형만 허용.
- **전화번호 입력 필드에 명확한 레이블을 제공한다.** '휴대 전화번호', '지역 번호'처럼 명확한 레이블을 제공하고, 구분이 불필요하면 '전화번호'라는 레이블을 사용한다.
- **여러 가지 입력 형식에 유연한 입력 필드를 제공한다.** 공백, 하이픈, 대시 등 일반적인 형식을 허용한다. 특정 형식이 필요하면 도움말 텍스트로 명확하게 설명하고, 필요시 자동으로 형식을 수정할 수 있다.
- **국가 코드 입력에 콤보박스를 사용한다.** 국가 코드를 기억하지 못하는 사용자를 위해 국가명과 국가 코드가 명시된 목록을 콤보박스 옵션으로 제공한다.
- **여러 개의 전화번호 입력 요청 시, 각 번호를 구분할 수 있는 레이블을 제공한다.** 예: '휴대 전화번호', '사무실 전화번호'.
- **여러 개의 전화번호 입력 요청 시, 주로 사용하는 번호를 지정할 수 있는 옵션을 제공한다.**

## 접근성 가이드라인

- **입력 필드에 자동 완성 속성을 설정한다.** HTML 표준 `autocomplete` 속성을 사용해 입력 필드의 목적에 맞는 자동완성 정보를 사용자 에이전트에 전달해야 한다. 관련: WCAG 2.1 Identify Input Purpose(AA).

## 관련 KRDS 컴포넌트

| 컴포넌트 | 비고 |
| --- | --- |
| TextInput | 이름, 전화번호 입력 필드 |
| DateInput | 생년월일 — 원문이 날짜 선택기(캘린더)·Select 사용을 명시적으로 금지하고 "날짜 입력 서식 컴포넌트"를 권장 |
| Radio | 성별 선택(남성/여성/선택안함처럼 상호 배타적 단일 선택) |
| Dropdown | 전화번호 국가 코드 콤보박스 |

원문이 명시적으로 사용을 금지하는 컴포넌트: 생년월일 입력에는 Calendar(날짜 선택기)와 Select를 사용하지 않는다.
