# KRDS 접근성 리뷰 스킬

이 스킬은 코드를 직접 고치지 않는다. React/HTML 코드를 읽고 KWCAG 2.2 +
WCAG 2.1 인용이 달린 접근성 리뷰 리포트를 작성하는 것이 유일한 산출물이다.

## 리뷰 절차

### 1. 대상 범위 결정 — diff 우선, 전체 파일은 폴백

- **diff가 주어진 경우(PR 리뷰, 변경 사항 리뷰 요청)**: diff에 나타난 추가·수정
  라인을 우선 검토 대상으로 삼는다. 단, `scripts/check-static.mjs`는 파일
  전체를 읽어 검사하므로(diff 텍스트 자체를 입력으로 받지 않음), diff에 등장한
  파일들의 **현재(작업 트리) 전체 내용**에 대해 스크립트를 실행한 뒤, 출력된
  위반의 `line`이 diff의 변경 라인(추가된 `+` 라인 또는 그 라인이 속한 JSX
  엘리먼트/CSS 규칙 블록) 안에 있는지로 필터링해 보고한다. 변경되지 않은
  기존 코드의 기존 위반은 "참고 사항"으로 별도 표시하고 요약 건수에는
  포함하지 않는다(diff 리뷰의 책임 범위를 벗어나므로).
- **전체 파일 리뷰로 폴백하는 경우**: (a) diff가 주어지지 않고 파일 경로만
  주어진 경우, (b) diff만으로는 판단할 수 없는 항목 — 포커스 순서, 랜드마크
  구조, 제목 위계처럼 파일/페이지 전체의 구조를 봐야 판단 가능한 모델 판단
  항목(§3) — 을 검토해야 하는 경우, (c) 사용자가 명시적으로 "전체 파일 검토"를
  요청한 경우. 이때는 대상 파일 전체에 대해 정적 검사(§2)와 모델 판단(§3)을
  모두 수행한다.
- 어느 경우든 검토 대상 파일 목록과 diff 우선/전체 폴백 여부를 리포트 상단에
  명시한다.

### 2. 결정론적 검사 — `scripts/check-static.mjs`

```bash
node skills/krds-a11y-review/scripts/check-static.mjs <파일...>
```

- 인자로 받은 `.tsx`/`.jsx`/`.html`/`.css` 파일들을 정적으로 검사해 위반
  사항을 JSON 배열로 stdout에 출력한다(그 외 확장자는 조용히 건너뜀). 인자
  없이 또는 `--help`로 실행하면 사용법을 출력한다.
- 검사 항목 5종: (a) 하드코딩 색상(hex/rgb, KRDS 토큰 미사용), (b) 인라인
  style 기반 터치 타깃 의심 크기(44px 미만 + onPress/onClick), (c) img/Image
  요소의 alt 부재, (d) button/링크류의 접근 가능한 텍스트·aria-label 부재,
  (e) `<div onClick>` 류 비시맨틱 인터랙션.
- 종료 코드: 위반 1건 이상이면 1, 없으면 0, 파일을 읽지 못하면 2(stderr에
  원인 출력). 종료 코드만으로 "위반 있음/없음"을 빠르게 판단할 수 있지만,
  실제 리포트 작성에는 항상 stdout JSON 전체를 파싱해서 사용한다.
- **출력 해석**: 각 원소는 `{ file, line, rule, severity, message, kwcag,
  wcag, confidence }` 형태다.
  - `severity`는 `error`(WCAG A 수준 등 명백한 결함) / `warning`(권장 사항
    위반) / `info`(부분적으로 보완되었으나 여전히 개선 권장)다.
  - `confidence`가 `"휴리스틱"`인 항목(터치 타깃 크기, button/링크 텍스트
    부재)은 정적 분석의 근사치이므로 리포트에서 반드시 "휴리스틱 — 코드
    맥락 확인 필요"로 표시하고, `"확정"`인 항목(하드코딩 색상 리터럴 존재,
    alt 부재, `<div onClick>` 존재 자체)과 구분한다. `"확정"`은 "패턴이
    코드에 실제로 존재한다"는 사실에 대한 확정이지 "반드시 접근성
    결함이다"라는 최종 판단이 아니다 — 예를 들어 장식용 이미지의 `alt=""`
    누락과 정보성 이미지의 `alt` 누락은 스크립트가 구분하지 못하므로,
    최종 심각도 판단은 모델이 코드 맥락(이미지 주변 텍스트, 컴포넌트 용도)을
    보고 확정한다.
  - `kwcag`/`wcag` 필드는 대표 조항 하나를 규칙별로 고정 매핑한 것이다
    (근거는 `scripts/check-static.mjs`의 `CITATIONS` 상수 주석 참고). 컴포넌트
    맥락에 따라 더 구체적인 조항이 있다면 §4에 따라 `kwcag-map.md`로 보강한다.

### 3. 모델 판단 검사 — 체크리스트

정적 검사로 판단할 수 없는 항목은 아래 기준으로 코드를 직접 읽고 판단한다.
각 항목은 해당하는 요소가 있을 때만 적용한다.

| 항목 | 판단 기준 |
| --- | --- |
| **alt 텍스트 품질** | 대체 텍스트가 이미지의 기능·정보를 구체적이고 간결하게 설명하는가? "이미지", "사진" 같은 요소 역할과 중복되는 표현, 촬영자 정보, 인접 텍스트와 동일한 설명, 이미지에 없는 추가 정보가 섞여 있지 않은가?(component_04_08.md 기준) |
| **포커스 순서** | 시각적 레이아웃 순서와 DOM/tabIndex 순서가 일치하는가? 모달·드롭다운·팝오버가 열릴 때 포커스가 해당 요소 내부로 이동하고, 닫힐 때 트리거 요소로 복귀하는가? 포커스 트랩이 없어야 할 곳에 있거나(No Keyboard Trap), 있어야 할 곳(모달)에 없지는 않은가? |
| **레이블 적절성** | 폼 필드의 `label`/`aria-label`이 필드의 목적을 사용자가 예측 가능한 문구로 설명하는가? placeholder만으로 label을 대체하고 있지 않은가? 버튼의 접근 가능한 이름이 아이콘이 아니라 버튼이 실행하는 동작을 설명하는가?(component_05_02.md Button 기준) |
| **제목 위계** | `h1`~`h6`가 레벨을 건너뛰지 않고 순차적으로 사용되며, 페이지/섹션의 논리적 구조를 반영하는가? 시각적 크기 때문에 실제 위계와 다른 heading level을 쓰고 있지 않은가? |
| **랜드마크** | `header`/`nav`/`main`/`footer`/`role="navigation"` 등 랜드마크가 페이지의 주요 영역을 중복 없이 감싸는가? 같은 종류의 랜드마크가 여러 개면 `aria-label`로 서로 구분되는가? |

### 4. `kwcag-map.md` 참조 시점

`scripts/check-static.mjs`가 붙이는 인용은 규칙당 대표 조항 1개로 고정되어
있어, 리뷰 대상이 특정 KRDS 컴포넌트(버튼, 페이지네이션, 모달 등)를 감싸거나
흉내 내는 코드라면 그 컴포넌트에 특화된 세부 규칙·인용이 `references/kwcag-map.md`
에 더 있을 수 있다. 다음 시점에 이 파일에서 해당 컴포넌트 절을 찾아 리포트에
추가 인용한다.

- §3 모델 판단에서 위반을 발견했지만 `check-static.mjs`가 붙이는 5종 규칙
  중 어디에도 해당하지 않을 때 — 정확한 KWCAG/WCAG 인용을 위해 컴포넌트별
  절을 찾는다.
- 리뷰 대상 코드가 명확히 특정 KRDS 컴포넌트 하나를 구현/사용하고 있을 때 —
  그 컴포넌트의 접근성 규칙 표 전체를 훑어, 코드가 놓친 항목이 있는지
  대조한다(예: 페이지네이션 구현이면 "현재 화면 숫자 링크를 색상만으로
  구분하지 않는다" 같은 항목).
- `kwcag-map.md`에 없는 패턴(디자인 시스템에 없는 커스텀 UI)은 §3 체크리스트와
  WCAG 2.1 일반 원칙으로 판단하고, 근접 KWCAG 조항이 있으면 근거를 리포트에
  남긴다.

### 5. 리포트 생성

§2·§3의 결과를 §6 템플릿에 맞춰 종합한다. "코드상 확정"(§2의 `confidence:
"확정"` 항목)과 "수동 검증 필요"(`confidence: "휴리스틱"` 항목 + §3 모델 판단
전체 + 스크린리더/키보드/실기기로만 확인 가능한 항목)를 반드시 절을 나눠
구분한다.

## 6. 리포트 템플릿

아래 템플릿을 채워 작성한다. 위반이 없는 항목(요약표의 행, 수동 검증 목록의
일부)은 생략 가능하되, 요약표와 "수동 검증 권고" 절은 항상 포함한다.

# 접근성 리뷰: <대상 파일/PR>

검토 범위: diff 기준 N개 파일 변경 라인 | 전체 파일 M개 (해당하는 쪽 명시)

## 요약

| 심각도 | 건수 |
| --- | --- |
| error | 2 |
| warning | 3 |
| info | 1 |
| **합계** | **6** |

## 위반 상세

### 1. `src/components/Foo.tsx:42` — missing-alt (error, 코드상 확정)

- KWCAG 2.2: 적절한 대체 텍스트 제공
- WCAG 2.1: Non-text Content (A)
- 설명: `<img src="/thumb.png" />`에 alt 속성이 없습니다.
- 수정 제안:
  ```tsx
  <img src="/thumb.png" alt="상품 썸네일" />
  ```

### 2. `src/components/Foo.tsx:58` — missing-accessible-name (error, 휴리스틱 — 코드 맥락 확인 필요)

- KWCAG 2.2: 적절한 링크 텍스트
- WCAG 2.1: Name, Role, Value (A)
- 설명: `<button>` 요소에 접근 가능한 텍스트나 aria-label이 없습니다. 아이콘만
  있는 버튼이라면 `aria-label`을, 텍스트 버튼이라면 자식 텍스트를 추가하세요.
- 수정 제안:
  ```tsx
  <button aria-label="필터 열기"><FilterIcon /></button>
  ```

### 3. `src/components/Foo.tsx:71` — 포커스 순서 (warning, 수동 검증 필요 — 모델 판단)

- WCAG 2.1: Focus Order (A)
- 설명: 모달이 열릴 때 포커스가 모달 내부로 이동하지 않고 배경의 마지막 포커스
  위치에 그대로 남아 있습니다.

## 코드상 확정된 위반

정적 검사(`check-static.mjs`)의 `confidence: "확정"` 항목만 모은 목록. 코드
자체에서 패턴 존재가 기계적으로 확인된 항목이다.

- #1

## 수동 검증이 필요한 항목

`confidence: "휴리스틱"` 항목과 §3 모델 판단 항목을 모은 목록. 스크린리더·
키보드·실기기 등 수동 확인 없이는 최종 결론을 내릴 수 없다.

- #2, #3

## 수동 검증 권고

- **스크린리더** (NVDA/VoiceOver/TalkBack 등): 변경된 화면을 스크린리더로
  순회하며 이미지·버튼·폼 필드가 의도한 이름/역할/상태로 안내되는지 확인.
- **키보드 순회**: 마우스 없이 Tab/Shift+Tab으로 모든 인터랙티브 요소에
  도달할 수 있는지, Enter/Space로 실행되는지, 포커스 링이 시각적으로
  보이는지, 키보드 트랩이 없는지 확인.
- **실기기**: 모바일 실기기(iOS/Android)에서 터치 타깃 크기와 확대/축소 시
  레이아웃 붕괴 여부를 확인(§2 (b) 터치 타깃 검사는 휴리스틱이므로 최종
  확인은 실기기에서).
```

## 참조

- `references/kwcag-map.md` — `npm run build:kwcag`(pipeline/build-kwcag-map.mjs)로
  자동 생성되는 컴포넌트별 KWCAG 2.2·WCAG 2.1 매핑표. 직접 수정하지 말 것.
- `scripts/check-static.mjs` — §2의 결정론적 검사 스크립트. 규칙별 대표
  인용 근거는 스크립트 상단 `CITATIONS` 상수 주석에 있다.
